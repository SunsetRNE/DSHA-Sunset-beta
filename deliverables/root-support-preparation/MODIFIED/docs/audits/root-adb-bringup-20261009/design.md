# 修正 root 自举 ADB 的实施设计

本文件供自有应用的工程落地评审使用。它修订历史方案，不表示已修改设备。纯 Java 请求策略与 adbd 证据解析器已在工作树中编写；`RootShellMain` 尚未接通 `adb-bootstrap`，授权项、执行器、UI 与持久模块仍待实现。

## 目标与状态分层

分别记录以下状态，不从单一观测推导整体 root 支持：

| 状态 | 可用证据 | 不可推导的结论 |
|---|---|---|
| 找到 su | 已核验路径、调用结果 | 已获 root 管理器授权 |
| root 授权 | 原生能力开关、管理器许可、实际执行身份 | 可跳过设备命令策略 |
| adbd 身份 | 退出码为零的固定列进程与 SELinux 捕获 | 客户端会话拥有相同权限 |
| 客户端会话 | 明确强制 ADB 路径的 `id` 与会话域 | 所有 ADB 连接都拥有相同身份 |
| 网络暴露 | IPv4/IPv6 监听、规则顺序、端到端探测 | loopback 只允许本应用访问 |
| chroot/runtime | 权限、ELF 加载器、执行与生命周期验证 | namespace 构成完整内核沙箱 |

Root → Shizuku → ADB 的发送前选择保持；显式 host/port 强制 ADB 路径。命令策略、原生开关与实际 Android 权限独立生效。结果未知时保留现场，不换通道、不重放。

## 命名入口与可信身份

拟增加的命名操作为 `adb-bootstrap`，仅接受 `operation/action/port/selfPackage/selfUid`。动作只接受小写 `authorize/revoke/narrow/open/close`；端口省略或 0 归一为 5555，仅另接受显式 5555。拒绝任意路径、属性名、命令串、公钥正文和附加字段。

PackageManager 的当前安装包、UID、APK source 必须由特权侧独立取得并绑定当前 APK；请求提供的包名/UID 只用于比对，不能自证身份。多用户 UID 按 appId 校验，拒绝系统、shell 与 isolated UID。调用者与 APK 替换的竞态需在执行前复核。

`AdbBootstrapPolicy.requirements()` 只声明执行条件，返回允许不表示条件已满足。下一阶段执行器必须检查这些条件并返回结构化证据。该模型不放宽通用 `DeviceShellPolicy`，也没有新增运行时入口。

| 动作 | 独立执行条件 |
|---|---|
| AUTHORIZE | APK 身份、root 原生许可、自举许可、已验证客户端公钥、密钥表快照 |
| REVOKE | APK 身份、root 原生许可、密钥表快照、本应用拥有的密钥；不依赖自举/ADB 开关仍打开 |
| NARROW | APK 身份、root/自举许可、双栈防护、监听证据 |
| OPEN | APK 身份、root/自举/ADB 许可、双栈防护、监听证据 |
| CLOSE | APK 身份、root 原生许可、监听证据；关闭自举/ADB 开关后仍可清理 |

root 许可也被撤销时不能暗中提权清理，应显示未清理状态并保留记录。清理与授权的失败处理分别设计。

## 密钥事务与撤销范围

原生侧验证实际客户端公钥格式与所有权；不读取私钥，不把密钥正文写入日志。变更前保存内容摘要、原字节、owner/mode/label 与当前代次，并在互斥区内复核。

授权按规范化后的密钥身份去重。必须记录是否由本次操作新增；预先存在的相同密钥不能被标为本应用独占。撤销仅删除记录证明由本应用拥有的条目，保留其他条目的原字节、顺序和元数据。所有权未知时停止修改。

原子替换后重新读取并验证。快照恢复必须比较预期当前摘要，避免覆盖后续其他客户端授权。清空整个 `adb_keys` 不能作为默认撤销。临时文件、备份与所有权记录由原生侧管理，不接受用户指定设备路径。

## 双栈防护与先后顺序

默认关闭，按需开启。先检查现有 IPv4/IPv6 监听、端口属性、规则和连接；保持关闭或先完成明确关闭，再施加可识别的本应用双栈规则。防护必须早于使监听对外可达的操作，不能先在 `post-fs-data.sh` 开端口再等待 `service.sh`。

IPv4 与 IPv6 防护均需成功、检查规则顺序并复读。工具缺失、族不可查询、输出含糊或厂商链覆盖都不能报告已收窄；未证明防护的族不得开启。另一主机连接超时只是辅助证据，不能代替规则及监听证明。

开启后核验两族监听和实际强制 ADB 会话；失败时按记录进入明确清理流程。关闭需证明监听消失及已有会话处理结果，属性为空或一次重启成功不能证明关闭完成。规则回滚只删除本次记录拥有的规则，并在确认关闭后进行。

原型中的 IPv4-only 脚本、任意端口、整表撤销和属性推断均不作为生产实现。原型字节留作历史材料，不能自动执行。

## 持久化与结果未知

本次不创建或安装 KernelSU 模块。持久档需后续单独评审：开机、netd/厂商链重建、规则消失、模块卸载与撤销后，都必须满足先防护后暴露的顺序；不能把“启动时补一次”视为持续保证。SELinux 变更依据目标拒绝日志精确评估，不复制历史机型规则。

执行结果至少区分拒绝、未发送的连接失败、已确认完成、执行结果未知。命令超时不能直接解释为没执行。`[EXECUTION_UNKNOWN]` 后先只读观察，记录实际身份、规则、密钥摘要和监听状态，禁止重放或自动切换通道。明确的后续清理也需要独立原生许可与记录。

## 落地顺序与验收

1. M1：固定策略与证据解析器、边界单测、主机回归。可先交付；运行时保持未接通。
2. M2：原生授权项、可信 APK 身份与命名入口；测试请求自证、APK 替换及关闭后的清理路径。
3. M3：密钥事务、所有权记录与双栈执行器；验证并发、幂等、失败不暴露与选择性撤销。
4. M4：UI 状态分别显示授权、守护进程、会话、暴露面、未知结果；不由一条 `id` 生成“完整 root 支持”。
5. M5：SDK 就绪后跑完整单测、两 flavor 构建、签名与资产检查；rooted 与非 rooted 设备分别验收。
6. M6：只有受管插件字节需要变化时才做插件与描述符联动；持久档另立验收，不作为 M1 的依赖。
