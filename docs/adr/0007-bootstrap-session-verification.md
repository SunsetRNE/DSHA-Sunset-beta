[控制器](../../app/src/main/java/com/deepseekharness/app/core/AdbBootstrapController.java)当前在原生 OPEN 成功后，先开启本应用 ADB 通道以取得原生执行计划，再等待、执行会话核验。失败时可能已经留下监听、公钥和开启的本应用开关；这与“设备未改动”或“整链完成”均不等价。

F01/F04 已把这条路径收进意图与完成条件：整链在确认时捕获一次 ADB 总开关的用户意图代次，自动启用只在代次未变时提交，被拒时以 `ADB_SWITCH_INTENT_CHANGED` 明确报告而不是反转用户开关；下一步提交失败不再由「队列为空」推导成整链成功。未决状态由原生响应独立报告（网络 / 公钥两个阶段 + 是否已核实），旧格式或读不到持久记录时保持未知，不会把已有未决清成已确认。

[专用客户端入口](../../app/src/main/assets/adb-shell.py#L442)固定连接 `127.0.0.1:5555`，只执行一次无 `su` 的只读 `id`；不枚举其他地址、不走 mDNS/历史端点回退、不在结果未知后重放。用户显式再核验是新的一次只读请求，不意味着可以重发 AUTHORIZE/NARROW/OPEN。

## 2. 已有证据能证明什么

历史[设备记录](../audits/adr0005-adb-global-20261011/device-state.txt)记录了授权表中的本应用公钥、5555 监听，以及一次同端点 `id` 返回 UID 0。其结论限于该次设备状态和会话。

这些材料不能单独证明另一次失败只由“新公钥尚未生效”造成。需要对应失败请求的原生响应、端点、实际通道、脚本身份、退出码和脱敏错误原文，才能区分：

- 原生授权已变化，或本应用 ADB 总开关不允许取得计划；
- 固定桥的实例/凭据不匹配、环境维护占用或受管脚本不一致；
- 客户端依赖、连接、握手或输出完整性失败；
- 系统侧密钥可见性或 adbd 状态变化。

[修复交接计划](../audits/root-adb-bringup-20261009/remediation-plan-20261011.md)还确认了保活误用 Root/Shizuku 成功输出的路径。因此普通设备命令成功、保活显示 connected 和专用 ADB 会话成功必须分别判断。

## 3. 对旧版论据的更正

### 3.1 `portBoot` 是整机开机代次

[执行器构造](../../app/src/main/java/com/deepseekharness/app/RootBootstrapExecutor.java#L75)读取内核 `boot_id`；[监听所有权判据](../../app/src/main/java/com/deepseekharness/app/RootBootstrapExecutor.java#L182)使用本应用记录的 `portOwned` 与这一开机 UUID。它不是 adbd 的 PID 或出生时刻。

因此，仅重启 adbd 不会让 `portBoot` 自动失配。执行器在其他步骤还有 daemon 的 PID/出生身份核验，重启可能影响那些观察，但不能把它们与监听的开机代次记录混为一谈。

### 3.2 固定原生动作已经具有重启能力

当前执行器的 [OPEN](../../app/src/main/java/com/deepseekharness/app/RootBootstrapExecutor.java#L278)、[CLOSE](../../app/src/main/java/com/deepseekharness/app/RootBootstrapExecutor.java#L310)、[REVOKE](../../app/src/main/java/com/deepseekharness/app/RootBootstrapExecutor.java#L397) 已在各自受控条件下调用固定的 `ctl.restart adbd`。通用设备命令策略拒绝任意属性写入，不等于固定自举入口没有此能力。

这只纠正已有能力的事实，不等于核验失败后应追加重启。额外重启会影响其他 ADB 会话，也须受原生授权、持久阶段、结果未知不重发和设备归属核验约束。

### 3.3 系统无线调试不是无副作用的“重读密钥”按钮

系统无线调试会引入独立 TLS 入口，自举按设计与它互斥。旧版建议“开关一次无线调试代替自举重启”可能重新制造 `WIRELESS_DEBUG_IN_USE`；它不能作为本自举链的默认自动补偿或通用排障步骤。

若用户要切换到系统无线调试，应明确展示现存监听、公钥和未决事务，先确认相应清理或切换条件，再由用户选择该模式。不能由一次失败静默推导这种使用意图。

## 4. 后续实施顺序

1. 先完成交接计划中 F01–F05 的授权撤销、事务状态、续链完成条件、无线互斥和真实 ADB 探测。完成条件是对应错误路径的回归测试成立，不是仅在某台设备上多等一次后成功。
2. 保留 A+C+D 现有单次核验语义，收集同一固定端点的失败证据。已有监听、待清理事务、本应用许可和会话核验结果分别呈现；只读再核验不能自行清除未核实的事务。
3. 若仍失败，根据证据选择下一步。只有确认需要改变核验次数或添加重启时，才把 B/E 作为明确的新行为变更设计和验证；不能以“当前可能已有重启能力”代替用户意图和事务约束。

新增回归覆盖、修复已确定缺陷不受旧版“控制器一行不动”的历史表述限制。本次文档修订没有启用 B/E，也没有改变既有 2.5 秒配置。
