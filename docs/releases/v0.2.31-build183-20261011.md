# v0.2.31 / build183（2026-10-11）待处理维护在热启动也可见 · 工程包

用户提出关键疑问：**「覆盖安装我这边看不到环境维护，你那边（虚拟屏）却能触发，最近几个版本都这样」
—— 查证后确认这是逻辑不一致**，本包修掉。

## 查证结论

**触发条件不是"安装"本身**，而是「设备上已安装的运行身份 ≠ APK 里受管描述符的身份」：
175 / 181 / 182 改过受管输入（`HttpShellService` / `AdbBootstrapController`），每个包都带来新的
`runtimeId`，设备因此处于"需要更新运行时"的状态。这是**设备状态**，两边都存在。

差别在**入口**：只有**全新创建 `MainActivity`** 时才会走路由：

```
MainActivity.onCreate:
  MaintenanceCoordinator.pending(controller)
  || (!isEnvironmentReady() || EnvironmentAccess.requiresMaintenanceBeforeStart(controller))
      → startActivity(ExtractActivity)
```

- 虚拟屏 `vscreen/launch` = 全新创建 → 每次都进维护页；
- 用户正常打开时进程/任务通常还活着 = **热启动，不重跑 `onCreate`** → 不跳转；
  而主界面横幅只在"维护**正在跑**"（`BackupTask.maintenanceBusy()`）或"受限模式"时显示，
  **"有待处理维护但没在跑"什么都不显示**。

→ **待处理的维护只在冷启动可见、可恢复；热启动把它整个藏起来。** 这就是用户感觉"逻辑不对"的地方。

另外"最近几个版本都会这样"：覆盖安装会杀进程，若事务在切换受管文件中途被打断，就停在
「恢复中断维护」；下一次冷启动接着跑 —— 于是反复出现。

## 改了什么（零 `runtimeId` 代价）

`ui/MainActivity`：

- `onResume` 探一次 `MaintenanceCoordinator.pending(controller)`（try/catch 降级为 false），
  不再只依赖 `onCreate` 的跳转；
- 横幅条件加入该标志，文案新增「**环境维护待处理 · 点击恢复**」（点击进维护页恢复）。

这属于既有的启动/界面层（`ui/` 不在受管输入清单里），因此 `runtimeId` **未变**
（仍是 `812c2d9674cc4eba873d90bbf678983dbd027c0f28b3e2fc673a174e5e9c2bd4`）——
**装本包不会再触发一次新的运行时维护**。
