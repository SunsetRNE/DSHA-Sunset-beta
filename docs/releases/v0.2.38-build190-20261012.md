# v0.2.38 / build190（2026-10-12）CI 重新能编：SDK 定位与 androidTest 调用点（测试包）

## 背景：main 上的 Source checks 是红的

2026-10-12T09:04:43Z 推送的 `bede35e`（"汇总设备桥与授权修复并接通双版本 APK 直传 CI"）
在 main 上的 Source checks 直接失败（run `38227580566`），死在「Pinned Android SDK platform
and build tools」这一步：

```
/home/runner/work/_temp/15c8ad22-….sh: line 4: sdkmanager: command not found
##[error]Process completed with exit code 127.
```

真正的代价不是这一步本身，而是它后面的 5 个 step（`Verify checked-in contracts`、固定上游
字节、资产部署契约、宿主 fast 回归、双 flavor 单测）**全部 skipped** —— 一次定位失败让整条
流水线的证据都变成"没跑"。SunsetRNE 实验包工作流（`ci-apk-sunsetrne.yml` 的 `source-checks`
作业）等的恰恰是**同一个 SHA** 上这一次通过，因此它也一直没有被派发过。

## 改了什么

### 1. `sdkmanager` 的定位不再依赖 PATH

- 新增 [tools/ci-android-sdk.sh](../tools/ci-android-sdk.sh)：按
  `$ANDROID_HOME`/`$ANDROID_SDK_ROOT` 下的 `cmdline-tools/latest/bin` → `cmdline-tools/bin`
  → `tools/bin` → `PATH` 的顺序解析真正可执行的 sdkmanager；解析不到就把两个环境变量的
  实际值带进错误信息并 `exit 1`，**不猜版本号、不改 SDK 配置、失败后不改走别的通道**。
  `ANDROID_HOME` 缺失时从可执行文件上溯三级回推 SDK 根目录并导出，调用方在同一 step 里
  仍然用得到（`source` 用法，`ci-apk-sunsetrne.yml` 后面就要按它拼 `build-tools` 路径）。
- 四个工作流统一改用它：`ci-fast.yml`（这次失败的那步）、`ci-package.yml`、`release.yml`、
  `ci-apk-sunsetrne.yml`。裸 `sdkmanager ...` 在仓库里已经一处不剩。

### 2. androidTest 里过期的方法调用点

`HarnessService.refreshPowerMode` 早已改成 `refreshPowerMode(Context)`，主源集都跟上了，
但 `app/src/androidTest/.../core/RecoveryInstrumentation.java` 的两处仍按无参调用，
standard/low 两个 flavor 的 androidTest 都编译不过：

```
RecoveryInstrumentation.java:195: error: method refreshPowerMode in class HarnessService cannot be applied to given types;
    required: Context
    found:    no arguments
```

两处改为传该用例里已有的 `Context base`（同一个 `getTargetContext().getApplicationContext()`，
与主源集的 `requireContext()` 语义一致）。这条路径不在 `ci-fast` 的编译范围内（那里只跑
单测），所以它一直是"编不到就不报"的静默缺口。

### 3. 宿主回归里一个不可读的候选 SDK 目录会带走整条测试

SDK 那步修好之后，流水线第一次真正跑到了 `Isolated source and protocol regressions`
（在这个提交之前它一直是被 skip 的），随即暴露第二个遗留问题：`tools/test-shizuku-lifecycle.py`
的 `android_jar()` 按顺序遍历候选 SDK 根目录，**已经拿到候选之后**仍然会走到硬编码的本机开发
路径 `/root/Android`；GitHub runner 上 `/root` 是 0700 root 所有，`Path.glob` 会对 EACCES
直接抛 `PermissionError`（`pathlib.is_dir()` 只吞 ENOENT/ENOTDIR/EBADF/ELOOP），于是整个测试崩：

```
File ".../tools/test-shizuku-lifecycle.py", line 330, in android_jar
    candidates.extend(Path(root).glob('platforms/android-3*/android.jar'))
PermissionError: [Errno 13] Permission denied: '/root/Android'
```

修法：单个候选列不出来就跳过（`except OSError: continue`），不让一个不可读目录把已经找到的
候选一起带走；另外把 runner 镜像的标准位置 `/usr/local/lib/android/sdk` 也列入候选；都找不到
时把试过的根目录一并写进 `ANDROID_JAR_MISSING`，下一次失败能自证原因。

**红绿证据**（本机，用 monkeypatch 让一个排在后面的候选抛 `PermissionError`，模拟 runner）：

| | 结果 |
|---|---|
| 旧逻辑 | `RED 复现成功：旧逻辑在后面那个候选上抛 PermissionError -> [Errno 13] Permission denied: '/opt/android-sdk'` |
| 新逻辑 | `GREEN: /root/Android/platforms/android-37.0/android.jar` |

### 4. Gradle 依赖校验缺了 aapt2 的 linux 分类器摘要

再接下去跑到 Gradle 单测那一步（run `38236379162`）又卡住：

```
Execution failed for task ':app:compileStandardDebugNavigationResources'
  > Could not isolate value ... CompileNavigationResourcesParams
    > Dependency verification failed for configuration ':app:detachedConfiguration2'
      One artifact failed verification: aapt2-9.1.1-14792394-linux.jar
      (com.android.tools.build:aapt2:9.1.1-14792394) from repository Google
```

`gradle/verification-metadata.xml` 里只有 aapt2 的 `-windows.jar` 与 `.pom`，没有
`-linux.jar`。原因是本机一直用 `~/.gradle/gradle.properties` 的
`android.aapt2FromMavenOverride` 指向自带的 aarch64 aapt2，**这个分类器从来没被解析过**，
也就从来没进过受信清单；CI（ubuntu-24.04 runner）才是唯一会真正下载它的地方。

补上 `aapt2-9.1.1-14792394-linux.jar` 的
`sha256 = e7ae17af6e4093c771243e82d66462353de87befaac206bfb43e557ac1c34440`。这个摘要
**不是拿下载到的字节自证**：它与 Google Maven 同一路径下官方发布的 `.sha256` 文件逐字节
一致（两处独立来源）。

本机验证：临时移开 aapt2 覆盖配置 → 重跑同一个失败任务
`:app:compileStandardDebugNavigationResources` → `BUILD SUCCESSFUL`，产物落进 Gradle 缓存
且摘要与上面相同；随后恢复本机配置（仓库源文件不受影响）。它也是这份清单里唯一的平台
分类器依赖，其余（`r8`、`apksig`、`desugar_jdk_libs` 等）都是与主机架构无关的纯 Java 产物。

## CI 产物格式：本次不改，但把它固化成了测试

`bede35e` 已按 GitHub 2026-02-26 的 upload-artifact 契约接线，本次保持原样：

- 两个 APK **各自**用 `archive: false` 单文件上传（一次上传只放一个文件），
  `name` 参数在这种模式下会被忽略，**artifact 名取实际文件名**
  —— `SunsetRNE-standard-experimental.apk` / `SunsetRNE-low-experimental.apk`，
  下载下来直接就是 `.apk`，不再套一层 zip。
- 回执与校验和（`*.apk.sha256`、`experimental-package-receipt.json`）继续走 `archive: true`
  压缩包，**压缩包格式不变**；发布作业仍按 `pattern: SunsetRNE-*` + `merge-multiple: true`
  拉回两类产物。
- `ci-package.yml` 的 `UNSIGNED-NOT-FOR-INSTALLATION`（两个 release APK + 一个目录）与
  `release.yml` 的 `SIGNED-HISTORICAL-CERTIFICATE`（一个目录）**多文件，天然不能 `archive: false`**，
  因此继续是压缩包 —— 这就是"压缩包格式不变"的边界。
- 这条契约由 `tools/test-ci-test-package.py::test_apks_are_separate_direct_downloads_and_reports_stay_archived`
  守着（断言正好 2 个 `archive: false` 上传、路径为两个 APK、块内不得出现 `name:`、
  回执必须是 `archive: true`），本次改动后 22 项全过。
